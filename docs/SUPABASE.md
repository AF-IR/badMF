# اتصال حرفه‌ای سوپابیس (معماری دیتابیس)

این پروژه سه لایه ارتباط با سوپابیس دارد که مرز «عمومی / ادمین / سرور» را دقیق جدا می‌کند:

```
مرورگر بازدیدکننده          مرورگر ادمین                    سرور (Next.js)
──────────────────        ────────────────────           ─────────────────────────────
lib/supabase/browser.js   Supabase Auth (سشن کوکی)        lib/supabase/server.js  ← @supabase/ssr + کوکی‌ها
فقط داده عمومی            + پنل → /api/admin-db          lib/supabase/service.js ← service role
(anon + RLS)              (پل امن)                        (ثبت رزرو، پل ادمین، دستیار، پرداخت)
```

## ۱) کلاینت‌های استاندارد (@supabase/ssr)

- **`lib/supabase/server.js`** — `createServerClient` با مدیریت کوکی‌های Next.js؛ برای خواندن در Server Components و تایید هویت ادمین در Route Handlers.
- **`lib/supabase/browser.js`** — `createBrowserClient` سینگلتون؛ برای ورود ادمین (Supabase Auth) و آپلود تصویر در استوریج.
- **`lib/supabase/service.js`** — کلاینت با `SUPABASE_SERVICE_ROLE_KEY`؛ فقط در سرور، بدون سشن، برای نوشتن‌های امن (رزرو، CRUD پل ادمین). هرگز import نشود در کامپوننت‌های کلاینت.

## ۲) لایه داده با fallback کامل (`lib/data.js`)

همه خواندنی‌های سایت از `getSiteData()` عبور می‌کنند:

1. اگر `SUPABASE_SERVICE_ROLE_KEY` تنظیم باشد → خواندن از جدول‌ها.
2. اگر جدول خالی/خطا/بدون پیکربندی → **داده پیش‌فرض درون‌کد** (DEFAULT_DB) برگردانده می‌شود.

نتیجه: سایت هرگز «خالی» نمی‌شود — قبل از اتصال، داده نمونه و بعد از اتصال، داده واقعی نمایش داده می‌شود. صفحه‌ها ISR با `revalidate = 60` هستند، پس تغییر ادمین حداکثر یک دقیقه بعد عمومی می‌شود.

## ۳) امنیت مبتنی بر RLS (سیاست‌های سطح ردیف)

طبق `supabase/schema.sql`:

| جدول | خواندن | نوشتن |
|---|---|---|
| categories, tariffs, sessions, posts, testimonials | عمومی | فقط ادمین (`is_admin()`) |
| settings | عمومی | فقط ادمین |
| bookings | فقط ادمین | **همه** می‌توانند insert کنند (ثبت رزرو مهمان) |
| storage/site-images | عمومی (read) | فقط ادمین (upload/update/delete) |

تابع `is_admin()` با `auth.email()` کاربر لاگین‌شده، آرایه `admin_emails` را چک می‌کند — ایمیل ادمین خود را در این تابع ثبت کنید (docs/SETUP.md قدم ۲).

## ۴) پل امن ادمین (`/api/admin-db`)

پنل ادمین برای نوشتن از این مسیر استفاده می‌کند، نه مستقیم از کلاینت anon:

1. Route Handler سشن ادمین را با `createClient()` سرور و `auth.getUser()` تایید می‌کند.
2. فقط بعد از تایید، عملیات با کلاینت service-role اجرا می‌شود.
3. جدول مجاز با لیست سفید محدود شده؛ جدول ناشناخته رد می‌شود.

مزیت: حتی اگر پالیسی RLS اشتباهی تنظیم شود، نوشتن بدون تایید هویت از این مسیر نمی‌گذرد.

## ۵) استوریج تصاویر

- Bucket عمومی `site-images` توسط `schema.sql` ساخته می‌شود.
- آپلود از پنل ادمین با کلاینت مرورگر انجام می‌شود (پالیسی `admin upload` اجازه می‌دهد) و URL عمومی در `settings` ذخیره می‌گردد.
- نمایش سایت: `lib/images.js` به‌ترتیب «تنظیم ادمین ← تصویر پیش‌فرض واقعی» را برمی‌گزیند؛ همه با `next/image` بهینه رندر می‌شوند.

## ۶) محدودیت‌های پذیرفته‌شده

- ISR (revalidate=60) یعنی تغییرات ادمین تا ۶۰ ثانیه بعد در سایت عمومی می‌آید — برای این کاربرد کاملاً کافی است.
- `generateStaticParams` بلاگ فقط مقالات پیش‌فرض را در build ایندکس می‌کند؛ مقالات اضافه‌شده از ادمین در زمان اجرا رندر می‌شوند (`dynamicParams = true`).
- شمارش ظرفیت رزروها در همین نسخه «اعلامی» است (قفل همزمانی روی ظرفیت نداریم)؛ برای منع رزرو مازاد بعداً می‌توان تابع RPC با транاکنش افزود.
